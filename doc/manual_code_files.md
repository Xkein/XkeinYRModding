## 背景：CppHeaderTool 生成什么、什么必须手写

> Background: what CppHeaderTool generates, and what must be written by hand.

### 1. `__HEADER_TOOL__` 宏机制

CppHeaderTool 解析头文件时通过预处理宏 `__HEADER_TOOL__` 区分"工具解析模式"与"正常编译模式"。该宏由 xmake 的 `codegen-cpp` 规则在调用工具时定义（定义处位于 `xmake/rules/codegen.lua` 的 defines 列表，约第 97 行，实测为准）；正常编译时该宏**不定义**。

因此，手写头文件用 `#ifndef __HEADER_TOOL__` 把"运行时代码"（include、Using\* 宏、模板特化等）包起来，让工具以"裁剪模式"解析，只看到 meta 声明；而编译时这些代码全部可见。典型示例：`src/scripting/javascript/all_data_binding.h` 第 3 行附近（实测为准）即 `#ifndef __HEADER_TOOL__`，其内部全部内容只参与 JS 绑定编译，不参与反射代码生成。

When CppHeaderTool parses a header it defines the `__HEADER_TOOL__` preprocessor macro (defined in the `defines` list of `xmake/rules/codegen.lua`, around line 97, verify at build time); normal compilation leaves it undefined. Hand-written headers wrap runtime-only code in `#ifndef __HEADER_TOOL__` so the tool parses in a "trimmed mode" and sees only the meta declarations, while the compiler sees everything. Example: `src/scripting/javascript/all_data_binding.h` near line 3 (verify in source).

### 3. 为何这 8 个文件必须手写 Why These 8 Files Must Be Written by Hand

代码生成器只能为带 meta 标注（`CLASS` / `PROPERTY` / `FUNCTION`）的类生成绑定。而这 8 个手写文件承担的是生成器**无法覆盖**的工作：模板实例化的显式注册、Converter 特化、声明侧与实现侧注册表的 1:1 对应。

例如 `TDelegate<FUNC>` 这类模板实例必须逐个显式登记（`UsingTDelegate` 声明 + `RegisterTDelegate` 实现配对），否则 puerts 在编译期找不到类型、或在链接期找不到 `DefineClass` 实例化。

The generator only binds classes annotated with meta (`CLASS` / `PROPERTY` / `FUNCTION`). These 8 hand-written files cover what it cannot: explicit registration of template instantiations, Converter specializations, and the 1:1 correspondence between the declaration side and the implementation side. For example each `TDelegate<FUNC>` instantiation must be registered explicitly (`UsingTDelegate` paired with `RegisterTDelegate`), otherwise puerts fails at compile time (type not found) or link time (`DefineClass` not instantiated).

### 2. 声明与实现分离 Declaration / Implementation Split

JS 绑定体系采用"声明在头文件、实现在 cpp"的两段式结构，8 个文件据此分为四类角色：

**声明侧**（`all_data_binding.h` 与 `yr_data_bindings.h`）通过 `Using*` 宏向 puerts 注册类型的可识别性（`ScriptTypeName` / `Converter`），使类型在绑定代码中"可被解析"。`all_data_binding.h` 是声明中心，`yr_data_bindings.h` 是其 YRpp 部分的清单子集。

**实现侧**（`delegate_binding.cpp` / `script_function_binding.cpp` / `yr_containers.cpp` / `yr_structs.cpp`）通过 `PUERTS_NAMESPACE::DefineClass` 链式调用构建实际的 JS 类结构：方法、属性、构造函数与继承关系，最后 `Register()` 落地。

**具名包装层**（`script_function_wrappers.h`）为每个 `FUNC` 生成一个具名派生结构体，解决模板实例 `ScriptFunction<FUNC>` 没有独立类型名、反射系统无法引用的问题；它被 `all_data_binding.h` 在顶部 include。

**entt 反射侧**（`yr_reflection.cpp`）是独立的 C++ 反射注册，与 JS 绑定平行、互不依赖：它面向 entt 的 C++ 反射，不经过 `all_data_binding.h` 的任何 `Using*` 宏。

The declaration side (`all_data_binding.h` + `yr_data_bindings.h`) registers type recognizability (`ScriptTypeName` / `Converter`) via `Using*` macros; the implementation side (`delegate_binding.cpp` / `script_function_binding.cpp` / `yr_containers.cpp` / `yr_structs.cpp`) builds the actual JS class structure through `PUERTS_NAMESPACE::DefineClass` chains; `script_function_wrappers.h` is the named-wrapper layer giving each `ScriptFunction<FUNC>` instantiation a distinct type name; `yr_reflection.cpp` is a standalone entt reflection side, parallel to the JS binding and independent of `all_data_binding.h`.

### 3. 核心原则：声明侧与实现侧 1:1 对应 The 1:1 Correspondence Principle

声明侧与实现侧的 FUNC 签名列表必须 **1:1 对应**：声明里登记了哪个签名，实现里就必须为同一签名完成注册，反之亦然。典型配对如：

- `UsingTDelegate(FUNC)`（声明，`all_data_binding.h`）↔ `RegisterTDelegate<FUNC>()`（实现，`delegate_binding.cpp`）
- `UsingScriptFunction(FUNC)`（声明，`all_data_binding.h`）↔ `RegisterScriptFunction<FUNC>()`（实现，`script_function_binding.cpp`）

若两侧不一致，puerts 会在**编译期**找不到类型（声明缺失），或在**链接期**找不到 `DefineClass` 实例化（实现缺失）。新增暴露类型时，两侧必须同步修改（参见 [doc/all_data_binding.md](all_data_binding.md) 的"什么时候需要往里面加东西"）。

The FUNC signature lists on the declaration side and the implementation side must correspond **1:1**. A missing declaration makes puerts fail at compile time (type not found); a missing implementation makes it fail at link time (`DefineClass` not instantiated).

### 4. 入口机制 Entry Mechanism

四个 `__JsRegister_*` 实现文件入口均经 `GLOBAL_INVOKE_ON_CTOR(...)`（定义于 `src/core/raii_invoker.h`）在全局构造期自动执行，无需手动调用；`YrReflectionRegister()` 例外，它由 `src/yr/yr_extcore.cpp` 显式调用。仅此提及，不展开。

The four `__JsRegister_*` entry points run automatically at global-construction time via `GLOBAL_INVOKE_ON_CTOR(...)` (defined in `src/core/raii_invoker.h`); `YrReflectionRegister()` instead is invoked explicitly from `src/yr/yr_extcore.cpp`. Mentioned only, not expanded.

### 修改时机 When to Modify

### (a) 新增 JS 绑定类型 New JS Binding Type（`CLASS(BindJs)`）

场景：带 `CLASS(BindJs)` 的类新增了方法/属性，签名里引用了尚未登记的类型。操作序列：

1. 在带 `CLASS(BindJs)` 的类中加 `PROPERTY()` / `FUNCTION()` 成员——这是 CppHeaderTool 生成器的输入，不在本手册 8 个手写文件范围内，此处仅一句带过（详见 [doc/meta.md](meta.md)）。
2. 检查新方法/属性签名引用的类型是否已在 `all_data_binding.h` 登记（grep 类型名）：未登记则在对应分区加 `UsingCppType(新类型)`；若签名用 `std::vector` 加 `UsingStdVector(元素)`，`std::map` 加 `UsingStdMap(K, V)`，`std::set` 加 `UsingStdSet(T)`（宏定义见 `cpp_binding.h`）。
3. 若该新类型是容器类且需要 JS 侧可操作（`push_back` / `size` / `at` 等）→ 在 `yr_containers.cpp` 的 `__JsRegister_YrContainers()` 加对应的 `RegisterStdVector<T>()` 等（实测锚点：`UsingStdVector(` 32 ↔ `RegisterStdVector<` 31，按实例核对；只供 Converter 解析、JS 侧不操作的容器可只声明不注册，与 [doc/all_data_binding.md](all_data_binding.md) 第 45-47 行的规则一致）。
4. **验收**：重新生成 / 编译时生成代码能解析新类型，puerts 编译期不报"类型未登记"（即声明侧齐全）；需要 JS 操作的容器在运行期能用对应方法操作。

> **English:** For a new member on a `CLASS(BindJs)` class whose signature references a not-yet-registered type: add the matching declaration macro in `all_data_binding.h` (`UsingCppType`, or `UsingStdVector` / `UsingStdMap` / `UsingStdSet` for STL containers), then add the paired `RegisterStd*` call in `yr_containers.cpp` when script code must operate the container. Acceptance: the regenerated binding compiles with the type resolvable, i.e. the declaration side is complete.

### (b) 新增 `TDelegate` / `TMulticastDelegate` 签名 New Delegate Signature（核心场景）

场景：把一个新的函数签名作为委托暴露给 JS。这是最需要严谨的场景，声明侧与实现侧的 FUNC 签名必须逐字符一致。操作序列：

1. `all_data_binding.h` 委托/ScriptFunction 集中区（第 6 分区）加 `UsingTDelegate(FUNC)`（或 `UsingTMulticastDelegate(FUNC)`；仅绑定不可广播的变体用 `UsingTDelegateRegistration(FUNC)` / `UsingTMulticastDelegateRegistration(FUNC)`）。
2. `delegate_binding.cpp` 的 `__JsRegister_Delegates()` 加 `RegisterTDelegate<FUNC>()`（或 `RegisterTMulticastDelegate<FUNC>()` / 对应 `*Registration`）——FUNC 签名与声明侧**完全一致**（参数顺序、const、引用、指针一个不差）。
3. 若该委托需要支持脚本回调 + 存档（`BindScriptFunction` / `AddScriptFunction`）→ 触发三处联动，见场景 (c)，此处先行记录该需求。
4. 校验：grep 声明侧与实现侧 FUNC 数量 1:1。精确 pattern：`UsingTDelegate(` 带 `(`、`RegisterTDelegate<` 带 `<`，避开 `*Registration` 子串命中；模板定义 `void RegisterTDelegate()`（不带 `<`）不计入。
5. **验收**：编译期 puerts 能找到类型（声明侧齐全）、链接期能找到 `DefineClass` 实例化（实现侧齐全）。计数锚点（实测）：`grep -c "UsingTDelegate(" all_data_binding.h` = **30** ↔ `grep -c "RegisterTDelegate<" delegate_binding.cpp` = **30**；`UsingTMulticastDelegate(` = **14** ↔ `RegisterTMulticastDelegate<` = **14**；`*Registration` 各 = **2**。

> **English:** To expose a new delegate signature, add `UsingTDelegate(FUNC)` (or the multicast / `*Registration` variant) in `all_data_binding.h` and the paired `RegisterTDelegate<FUNC>()` in `delegate_binding.cpp`, keeping the FUNC signature character-for-character identical. Acceptance: puerts resolves the type at compile time (declaration complete) and `DefineClass` is instantiated at link time (implementation complete). Measured anchors: 30 ↔ 30 for `UsingTDelegate(` / `RegisterTDelegate<`, 14 ↔ 14 for the multicast pair, 2 each for `*Registration`.

### (c) 新增 `ScriptFunction` 签名 New ScriptFunction Signature（与 b 联动）

场景：委托签名需要脚本侧构造回调对象（`new` 具名 wrapper）后传给 `BindScriptFunction` / `AddScriptFunction`。三处联动，FUNC 签名三处完全一致。操作序列：

1. `script_function_wrappers.h` 加具名 wrapper 结构体：`CLASS(BindJs) struct ScriptFunction_<FormatIdentifier> : public ScriptFunction<FUNC>` + `FUNCTION()` 构造（转发 `std::function<Func>`）；类型名按 `FormatIdentifier` 规则推导并实测核对（命名规则见"委托与 ScriptFunction 绑定"章节的"命名规则"小节，勿照抄示意表）。
2. `all_data_binding.h` 加 `UsingScriptFunction(FUNC)`（展开为 `UsingCppType(ScriptFunction<FUNC>)`）。
3. `script_function_binding.cpp` 的 `__JsRegister_ScriptFunctions()` 加 `RegisterScriptFunction<FUNC>()`。
4. 校验：三处 FUNC 签名完全一致；wrapper 数量 + GAS 侧 3 个 creator = `UsingScriptFunction` 数量。
5. **验收**：`grep -c "UsingScriptFunction(" all_data_binding.h` 与 `grep -c "RegisterScriptFunction<" script_function_binding.cpp` 相等（实测均 **49**；`struct ScriptFunction_` 实测 **46**，46 + 3 creator = 49）。

> **English:** When a delegate needs a script-side callback, add the named wrapper struct in `script_function_wrappers.h` (name derived by `FormatIdentifier`, verified against source), declare `UsingScriptFunction(FUNC)` in `all_data_binding.h`, and instantiate `RegisterScriptFunction<FUNC>()` in `script_function_binding.cpp`. Acceptance: the three FUNC signatures match and `UsingScriptFunction(` count equals `RegisterScriptFunction<` count (measured 49 each; 46 wrappers plus 3 GAS creators).

### (d) 新增 YR 容器实例 New YR Container Instance

场景：把 `DynamicVectorClass<NewType*>` 等 YR 容器实例暴露给 JS。声明（`yr_data_bindings.h`）与实现（`yr_containers.cpp`）跨文件 1:1 配对。操作序列：

1. `yr_data_bindings.h` 加 `UsingDynamicVectorClass(NewType*)`（或 `UsingTypeList(NewType*)` / `UsingIndexClass(TKEY, TVALUE)` / `UsingHashTable(TKEY, TVALUE)`）。
2. `yr_containers.cpp` 的 `__JsRegister_YrContainers()` 加 `REGISTER_DYNAMIC_VECTOR_CLASS(NewType*)`（或 `REGISTER_TYPE_LIST(NewType*)` / `RegisterIndexClass<TKey, TValue>()`）——与声明侧配对。
3. 若元素类型以指针的指针（`T**`）形态暴露给 JS → `yr_containers.cpp` 顶部 `UsingPointer` 区加 `UsingPointer(NewType**)`（本文件自行维护，不写入 `all_data_binding.h`）。
4. 校验：元素类型已在 `all_data_binding.h` 或 `yr_data_bindings.h` 登记（`REGISTER_DYNAMIC_VECTOR_CLASS(NewType*)` 要求元素类型可被 puerts 识别）。
5. **验收**：两侧计数配对，但**按实例核对而非总数**——`UsingDynamicVectorClass` 一个宏展开 `VectorClass` 与 `DynamicVectorClass` 两个容器注册，且实测声明 77 处（`yr_data_bindings.h`）与实现调用 73 处（`yr_containers.cpp`）总数并不相等（见"yr_containers.cpp"章节的实测提示）；单个新实例只要求其声明与实现一一对应。

> **English:** To expose a new YR container instance, declare it in `yr_data_bindings.h` (`UsingDynamicVectorClass` / `UsingTypeList` / `UsingIndexClass` / `UsingHashTable`) and register it in `yr_containers.cpp` (`REGISTER_DYNAMIC_VECTOR_CLASS` / `REGISTER_TYPE_LIST` / `RegisterIndexClass`), adding `UsingPointer(NewType**)` here when a `T**` form is exposed. Acceptance: the pairings reconcile per instance, not by total count, because one `UsingDynamicVectorClass` expands to two container registrations and the measured totals differ (77 declarations vs 73 calls).

### (e) 新增 YR 值类型结构体 New YR Value-Type Struct

场景：把 `Vector2D` / `ColorStruct` 这类 YR 原生值类型暴露给 JS。与场景 (d) 的关键差异：**无需任何声明侧登记**。操作序列：

1. `yr_structs.cpp` 的 `__JsRegister_YrStructs()` 加 `DefineClass` + 链式（`.Constructor()` / `.Property()` / `.Method()` / `.Register()`）；模板类型（如新的 `VectorXD<T>` 变体）用接收 builder 右值的模板函数（仿 `RegisterVector2D<T>()`），再在入口按 `T` 实例化。
2. **无需修改 `all_data_binding.h`**（值类型由 puerts 自动推导 Converter）。
3. 若同时需要 C++ 反射侧可见 → 在 `yr_reflection.cpp` 对称添加（场景 f）。
4. **验收**：JS 侧能构造并访问属性/方法；`grep "新类型名" all_data_binding.h` 确无登记（实测 `Vector2D` 在 `all_data_binding.h` 为 **0 命中**）；若发现该值类型出现在声明侧，则与设计矛盾，回查是否误当成非值类型登记。

> **English:** A new YR value-type struct is registered only in `yr_structs.cpp` with a `DefineClass` chain inside `__JsRegister_YrStructs()`; `all_data_binding.h` stays untouched because puerts deduces the converter automatically. Acceptance: the type is constructible and its properties work in JS, and grep for the type name in `all_data_binding.h` finds nothing (measured 0 hits for `Vector2D`); a declaration there would contradict the design.

### (f) 新增反射注册（entt）New Reflection Registration

场景：把 YR 类型手动注册进 entt meta（C++ 反射侧）。要点是**注册 / 卸载对称成对**。操作序列：

1. `yr_reflection.cpp` 的 `YrReflectionRegister()` 加 `INIT_META_FACTORY` 注册块（`type` + `custom<ClassMeta>` + `register_data` / `register_func`），或走批量宏 `REGISTER_DYNAMIC_VECTOR_CLASS(C)`。
2. **对称**：`YrReflectionUnregister()` 加对应的 `UNREGISTER_DYNAMIC_VECTOR_CLASS(C)` / `entt::meta_reset`——两函数同列表，必须成对维护，漏一侧会在卸载期残留或误清。
3. 若新类型是值类型且需 JS 侧 → 同时改 `yr_structs.cpp`（场景 e；JS 侧与反射侧平行注册同一批值类型）。
4. **验收**：注册/卸载成对——`grep -c "\bREGISTER_DYNAMIC_VECTOR_CLASS("` 与 `grep -c "UNREGISTER_DYNAMIC_VECTOR_CLASS("` 相等（实测均 **69**：宏定义 1 + 调用 68）；**注意**无 `\b` 时 `REGISTER_...` pattern 会把 `UNREGISTER_...` 当子串命中（实测 138），必须分开数。

> **English:** To add an entt reflection registration, extend `YrReflectionRegister()` with `INIT_META_FACTORY` blocks or the `REGISTER_DYNAMIC_VECTOR_CLASS(C)` batch macro and mirror every entry in `YrReflectionUnregister()` with `UNREGISTER_DYNAMIC_VECTOR_CLASS(C)` / `entt::meta_reset`. Acceptance: the register and unregister counts match (measured 69 each: 1 macro definition plus 68 calls), counting with the `\b` boundary because a bare `REGISTER_` pattern also matches the `UNREGISTER_` substring (measured 138).

### 通用检查清单 General Checklist

无论哪种场景，收尾前逐项检查：

- [ ] 新类型已 `#include` 对应头文件，且放对位置：声明侧在 `#ifndef __HEADER_TOOL__` 内（如 `all_data_binding.h` / `yr_data_bindings.h` 的 `Using*` 宏），或按既有约定（如 `yr_data_bindings.h` 在 `#ifndef` 之外被 include、`script_function_wrappers.h` 的 `UsingCppType` 注册在末尾 `#ifndef __HEADER_TOOL__` 块内）。
- [ ] 声明侧与实现侧 1:1：`Using*` ↔ `Register*` 配对，FUNC 签名逐字符一致（参数顺序、const、引用、指针）。
- [ ] 入口函数：四个 `__JsRegister_*`（`__JsRegister_Delegates` / `__JsRegister_ScriptFunctions` / `__JsRegister_YrContainers` / `__JsRegister_YrStructs`）由 `GLOBAL_INVOKE_ON_CTOR`（`src/core/raii_invoker.h`）在全局构造期自动执行，反射注册（`YrReflectionRegister` / `YrReflectionUnregister`）由 `src/yr/yr_extcore.cpp` 显式调用——新增注册都挂在既有入口内，**不新建入口**。
- [ ] 计数可复核：grep -c 两侧配对（详见各场景验收的计数锚点）。
- [ ] 不重复登记：`all_data_binding.h` ↔ `yr_data_bindings.h` 各管各的（YR 原生类只登记后者；已登记的类型不重复）。
- [ ] 脚本侧引用注意事项：ScriptFunction 的 `persistentObjs` 防 GC 惯例见 [doc/script_function.md](script_function.md) 第 4.4 节（仅交叉引用，不展开）。

> **English:** Before finishing, walk the general checklist: the new type's header is `#include`d in the right place (declarations inside `#ifndef __HEADER_TOOL__`, following each file's existing conventions); declaration and implementation sides pair 1:1 with character-identical FUNC signatures; new registrations are appended to the existing entry functions, never a new one (the four `__JsRegister_*` entries run via `GLOBAL_INVOKE_ON_CTOR` from `src/core/raii_invoker.h`, the reflection entries are called explicitly from `src/yr/yr_extcore.cpp`); counts are re-checkable with grep -c; `all_data_binding.h` and `yr_data_bindings.h` never duplicate each other; and script-side concerns such as the `persistentObjs` anti-GC convention for ScriptFunction are only cross-referenced to `doc/script_function.md` §4.4.
